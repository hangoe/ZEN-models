# MGA results: what each figure shows

Generated by `scripts/plot_mga_results.py`. Compares four MGA (Modelling to
Generate Alternatives) exploration modes run on `Crystal_Ball_ind_heat_v8_0_nodiffusion`
(28-node European model, 2050 greenfield, no diffusion limit) on Euler:

- **weights** — 6 directional solves (min/max photovoltaics, min/max
  onshore+offshore wind combined, min/max nuclear), each a single LP. No
  refinement, no polytope.
- **probabilistic (short)** — pyoNearOpt's support-function sampling method,
  run with a loose convergence bar (`tolerance_prob = 0.05`). Ran 9
  refinement iterations after 10 VMM (variable min/max) bound solves, then
  declared converged by its own (loose, CI-based) criterion.
- **probabilistic (long)** — the same method, same axes, same model, run
  with a much stricter convergence bar (`tolerance_prob = 0.95`). Ran 129
  refinement iterations (of a 500-iteration budget) after the same 10 VMM
  bound solves and had **not** converged when the run was stopped.
- **oracle** — pyoNearOpt's ORACLE method (exact max-min projection). Ran 85
  iterations after the same 10 VMM bound solves, then was manually stopped
  because it appeared stuck. It was stuck: iterations 13–85 (73 of 85, 86%
  of the run) returned the *exact same design point*, confirmed bit-for-bit
  from the individual result folders.

What "refinement iteration," "trial point," and "converged" mean precisely —
and why probabilistic's search looks so different from oracle's under the
hood — is worked out mathematically in
[Oracle vs. probabilistic: the mathematical difference](#oracle-vs-probabilistic-the-mathematical-difference)
below, before getting into what each figure shows. (Step-by-step diagrams of
both algorithms exist but live outside this repo now, not embedded here.)

All four explore the same 6-dimensional space: capacity additions for
**nuclear, photovoltaics, wind offshore, wind onshore** [GW], **biomass**
carrier import [GWh], and **net present cost** [MEUR] — the last included as
an explicit exploration axis rather than left implicit, so cost-band usage
is visible rather than hidden (same rationale as Steen2026_Thesis Sec 3.2).
Cost slack (near-optimality budget) is **ε = 10%** above the cost optimum
**C\* = 1,316,569 MEUR**. Baseline (cost-optimal) design **z\***: nuclear
27.6 GW, PV 4,365 GW, wind offshore 80.6 GW, wind onshore 1,267 GW, biomass
778 TWh (the dataset's import cap — baseline already uses all of it). This
baseline and the initial VMM-derived outer box are shared exactly by both
probabilistic runs: their independently-solved `z*`, `bounds_phys`, and
`A0`/`b0` match to full floating-point precision, confirming both runs
really are the same problem explored twice with a different stopping rule.

## Two probabilistic configurations: what actually differs

Both probabilistic runs use the same axes, the same ε, and the same
`tolerance_explore = 0.1` (the per-direction gap below which a sampled
direction counts as "well-approximated" — see the math section below). The
input that differs is `tolerance_prob`: the confidence-interval lower bound
that the *fraction* of well-approximated sampled directions must clear
before the run declares convergence
(`pyoNearOpt.metrics.ci_convergence_metric`). It is a confidence target, not
an error tolerance — **higher `tolerance_prob` means a stricter bar** (more
of the direction space must be certified well-approximated with high
confidence), the opposite sense of `epsilon`/`tolerance_explore`, where
smaller is stricter. That is the "higher tolerance" the long run was
configured with, and it is the single input change responsible for
everything else in this table:

| input / outcome | probabilistic (short) | probabilistic (long) |
|---|---|---|
| `tolerance_prob` (convergence bar) | **0.05** (only 5% of sampled directions need to check out) | **0.95** (95% of sampled directions need to check out) |
| `n_samples` (directions sampled per iteration) | 1,000 | 2,000 |
| `tolerance_explore` (per-direction gap target) | 0.1 | 0.1 |
| `max_iterations` budget | 200 | 500 |
| iterations actually run | 9 | 129 |
| converged? | **True** | **False** (stopped mid-run) |
| final `max_gap` (worst sampled direction) | 0.673 | 0.140 |
| final `ci_lower` (confidence the bar is cleared) | 0.047 (just under the 0.05 bar) | 0.940 (still under the 0.95 bar) |
| certified points on disk | 20 (11 shared VMM/baseline + 9 iterates) | 140 (11 shared VMM/baseline + 129 iterates) |
| cumulative real solving time | 2,212 s (~37 min) | 24,762 s (~6.9 h) |

Source: each run's own `..._probabilistic_summary/polytope.npz` (`run_json`,
`convergence_threshold`, `converged`, `final_gap`) and `diagnostics.csv`
(`ci_lower` trajectory) — not the checked-in
`data/config_mga_probabilistic.json`, which currently reflects only the
short run's settings; the long run used a locally-edited copy of that config
that was never committed, so its inputs are reconstructed here from what the
run itself actually recorded.

The short run's loose bar is trivial to clear: `ci_lower` climbs from 0.017
(iteration 0) to 0.047 (iteration 8), crossing 0.05 on the very next check
after the last logged iteration (`supf_explore` checks convergence *before*
picking each direction, so the crossing itself never gets its own row — see
the math section). The long run's strict bar is a different story: `ci_lower`
climbs steadily but with visibly diminishing returns —
0.064 (iter 9) → 0.181 (iter 19) → 0.542 (iter 49) → 0.863 (iter 99) →
0.940 (iter 128) — 29 more iterations between iter 99 and iter 128 bought
only +0.08 of confidence, versus +0.12 between iter 19 and iter 29. Reaching
0.95 from here would plausibly need a comparable further stretch of
iterations, which is consistent with why the run was stopped rather than
left to either converge or exhaust its 500-iteration budget.

**What this buys in practice (see fig4 for the full trajectories):** despite
running 7× more queries and ~11× more solving time than the short run, the
long run's shared max-separation metric only improves modestly: 0.621
(short, at query 20) → 0.604 (long, at query 140) — about 3% further, most
of it already banked by query ~60. The short run's own *native* stopping
rule is legitimately satisfied at `tolerance_prob=0.05`, but that bar is
loose enough that "converged" here should not be read as "space
well-characterized" — fig2/fig3 below use the long run's hull specifically
because it characterizes far more of the space, exactly because its stricter
bar forced far more exploration before stopping.

## Oracle vs. probabilistic: the mathematical difference

Both modes refine the same object: an **inner approximation** I (the convex
hull of certified near-optimal designs) and an **outer approximation** O (a
system of half-spaces Az ≤ b guaranteed to contain the true near-optimal
space Zᵉ), so that I ⊆ Zᵉ ⊆ O holds throughout. "Exploring" means shrinking
the gap between them. The two modes differ entirely in how they pick the next
point to certify, and in what they can prove about how much of the space is
still uncharacterised.

**Oracle** solves a bilevel problem for the single point that is
worst-approximated:

d_IO = max_{z∈O} min_{zᵢ∈I} ‖z − zᵢ‖∞

(`near_optimal_tools/docs/theory/oracle_derivation.rst`; `Steen2026_Thesis`
Eq. 7). This is reformulated into one MILP (KKT/big-M, or SOS1 constraints)
and solved to (near-)optimality. Its optimal point z_O* is then projected
onto the real near-optimal region by **one solve of the actual
energy-system model** with a distance-minimising objective in place of the
usual cost objective (`Steen2026_Thesis` Eq. 8), which returns the nearest
feasible design z_f* and — if z_O* itself was infeasible — a separating cut
built from that solve's dual variables. I grows by adding z_f*; O shrinks by
adding the cut. Because d_IO is solved to (near-)optimality, it is a
**certified upper bound** on how far off any reading of the space can still
be — the loop can honestly stop once d_IO ≤ tol, and that stopping decision
is provably correct, not just plausible.

**Probabilistic** (`sampling_exploration` in pyoNearOpt; the module was
`prob_ORACLE.py` in an earlier version of the package and was renamed to
`sampling_ORACLE.py` — the built docs in `near_optimal_tools/docs/_build/`
still reflect the old name, which is how the rename was spotted here) avoids
the bilevel solve entirely. Each iteration:

1. draws *n* quasi-random unit directions on the sphere (scrambled Sobol →
   inverse-normal-CDF → normalise to unit length —
   `shared_direction_oracle._sample_unit_sphere_directions`); *n* = 1,000 for
   the short run, 2,000 for the long run (see table above);
2. scores **every** sampled direction d with the support-function gap
   gap(d) = h_O(d) − h_I(d), where h_O(d) = max_{z∈O} dᵀz and
   h_I(d) = max_{z∈I} dᵀz are two small LPs each — **no model solve at all**
   for this step (`near_optimal_tools/docs/theory/support_function_theory.rst`;
   `shared_direction_oracle.sample_separation`);
3. picks the direction d* with the single largest gap and queries the real
   model exactly once in that direction (`sampling_exploration.next_direction`,
   `supf_explore.explore`);
4. refines I and O by the same rule as oracle's Step C.

Convergence is not a worst-case bound here: it is a Jeffreys confidence
interval on the *fraction* of sampled directions whose gap already sits below
`tolerance_explore` (`pyoNearOpt.metrics.fraction_well_explored`), and the
loop stops once that interval's **lower bound** clears `tolerance_prob`. As
the table above shows, this project ran that same loop twice at two very
different bars — `tolerance_prob = 0.05` (short, converged in 9 iterations)
and `tolerance_prob = 0.95` (long, not converged after 129) — which is
exactly what makes `tolerance_prob` interesting to compare: it is a dial on
"how much of the space must look fine before stopping," not a property of
the model or the search itself.

**The practical trade-off.** Oracle's one MILP grows with the number of
exploration axes and with how many points/cuts the approximations already
hold, so its per-iteration cost keeps climbing as the run progresses.
Probabilistic's per-iteration cost is *n* small LPs plus one model solve,
roughly flat regardless of how refined the approximations already are. Both
still pay for exactly one real model solve per iteration — that part is not
cheaper — but only oracle can *prove* a worst-case distance; probabilistic
only ever reports "most sampled directions look fine already," which is
exactly why its stopping rule is statistical rather than a certificate. fig4
below shows this trade-off on real data across all three query budgets:
probabilistic-short reaches a *better* value of the shared max-separation
metric in 20 queries / 37 minutes than oracle does in 96 queries / 9.5
hours — not because probabilistic's guarantee is stronger (it has none), but
because oracle got stuck re-certifying the same vertex for 73 straight
iterations, a failure mode its own exact per-iteration bookkeeping could not
detect early because each of those solves *did* return a technically-valid
trial point. Probabilistic-long pushes further still (0.604) for
substantially more time than either — see the table above for exactly how
much that extra rigor cost and bought.

**A source note.** `Steen2026_Thesis` is entirely about ORACLE (Sec 3.2),
plus a polytope-*interior*-sampling technique used only to interpret an
already-converged polytope (Sec 3.3 — unrelated to exploration; the basis for
this document's fig2/fig3, see the correction below). It does not cover the
probabilistic/sampling exploration mode at all — the math above comes
directly from `near_optimal_tools`'s own `docs/theory` and source, not from
the thesis. Relatedly, a correction to the fig2 section further down: Sec
3.3's own interior sampler is a hand-written **hit-and-run** walk with
covariance preconditioning, not the **Vaidya** walk this script's
`rejection_sample_inner` actually uses via
`pyoNearOpt.polytope_approximation.PolytopeSamples` (`walk_type="vaidya"`,
the package's default). Both are valid MCMC walks for the same
rejection-sampling *idea* (Steen's Eq. 13, same acceptance-rate diagnostic),
but they are not the same walk — the earlier wording overstated how literally
this script follows Steen's own implementation.

Two methodological choices carry through every figure and are explained in
more depth in the script's own docstring:

- **Shared coordinate frame.** All four modes are expressed in one
  6-D frame (axis scales, offsets, baseline point) taken from
  probabilistic-long's own saved polytope. It was picked over
  probabilistic-short's (verified bit-for-bit identical `z*`/bounds/`A0`/`b0`
  — either would do as *frame*) because it is also this script's basis for
  the fig2/fig3 inner-hull sampling, where its 140 certified points give a
  far better-refined hull than short's 20. Weights' own baseline solve
  reproduces the same z\* bit-for-bit too, confirming this frame is safe to
  share rather than an approximation. Oracle's own baseline folder is empty
  (see the data-loss note below), so its z\* is *borrowed* from this shared
  frame rather than independently verified — a reasonable assumption (same
  underlying model, same ε), but unlike weights, not a checked one.
- **Frozen initial box for convergence comparisons.** Where a "how much of
  the space is covered" metric is needed (fig4), it's evaluated against the
  *initial* VMM box, not each method's own refined outer approximation —
  because oracle's refinement history was lost (see below) and weights never
  builds one at all, so only the initial box is available for all four on
  equal footing.

**A data-loss note that matters for reading fig1 and fig4:** oracle's own
`oracle_summary/` (which would hold its native convergence diagnostics) is
empty — the run was killed before it could write them. Its trajectory in
these figures is reconstructed from 96 individual per-iteration result
folders instead, which is why oracle has no native convergence curve of its
own (only the shared frozen-box metric in fig4) and why its own reported
"gap to convergence" is unknown; only the reconstructed points are certain.


## fig0 — weights-mode capacity per axis, per directional solve

**What it shows.** A bar chart, not a polytope figure: each of the 6
weights-mode solves minimises or maximises one weighted combination of
capacities, subject to staying within the cost band. The bars show what that
solve did to *all four* tracked technology axes, not just the one it
targeted — revealing side effects a single-axis reading would miss. (This
mode doesn't depend on which probabilistic run is loaded and is unchanged
from before.)

**What the data says.**
- Baseline: PV 4,365 GW, wind onshore 1,267 GW, wind offshore 81 GW, nuclear
  28 GW.
- Max PV reaches 10,188 GW (its certified near-optimal ceiling) while wind
  onshore drops to 695 GW and nuclear to 14 GW — PV expansion crowds out
  onshore wind more than nuclear.
- Min PV drives PV to 0 GW; wind onshore rises only modestly (to 2,396 GW),
  so PV's absence isn't purely absorbed by wind — nuclear rises slightly too
  (34 GW).
- Max wind (onshore+offshore weighted together) reaches 4,324 GW onshore
  while PV falls to 1,539 GW — the strongest single substitution in this
  chart.
- Min/Max nuclear swing nuclear between 0 and 114 GW (its full certified
  range) while barely moving anything else (PV and wind onshore stay within
  ~5% of baseline either way) — nuclear is the most "isolated" axis here.
  fig3 below revisits both of these substitution/isolation observations with
  much more data and gets a more nuanced picture once the near-optimal
  *volume*, not just these 6 boundary solves, is taken into account.


## fig1 — pairwise projections of every mode's actual visited points

**What it shows.** Every certified near-optimal design point any of the
four modes actually produced (baseline solve, VMM bound solves, and
refinement iterations), projected onto every pair of axes and colour-coded
by mode. This is the ground truth — no sampling, no approximation, just the
real solved designs. Weights = green, probabilistic-short = petrol,
probabilistic-long = blue, oracle = red.

**What the data says.**
- Point counts: weights 7, probabilistic-short 20, probabilistic-long 140,
  oracle 96 (reconstructed) — probabilistic-long now contributes by far the
  densest, most spread-out cloud of any mode, a direct consequence of its
  129 refinement iterations against the short run's 9.
- Oracle (red) still forms one dense, overlapping cluster in most panels —
  the 73 stuck-vertex iterations plotting on top of each other — plus a
  scattered tail of ~20 distinct points from before it got stuck.
- The **net present cost row** is less uniformly pinned to the top of the
  band than a first look at the shorter runs suggests. Weights (86%),
  oracle (95%), and probabilistic-short (70%) still sit above 95% of the
  cost budget most of the time — consistent with directional/bilevel/loosely
  -sampled searches gravitating toward the boundary. Probabilistic-long is
  different: only 50% of its 140 points sit above 95% of budget (median
  93%), because 129 iterations of direction sampling inevitably also
  certifies some less extreme, more interior directions that the other,
  shorter searches never got to. fig2's density plot below confirms this
  isn't a fluke — the bulk of the near-optimal *volume* really does sit well
  under the cost cap.


## fig2 — hexbin density of the inner approximation's interior

**What it shows.** Unlike fig1 (only the handful of certified vertices),
this samples the *volume* of the near-optimal space to show where a
"typical" near-optimal design sits, not just the extreme ones exploration
happens to certify. It uses **probabilistic-long's** inner hull specifically
(see "Shared coordinate frame" above) — sampling method matters here, and
this figure went through a real fix worth recording:

An earlier version sampled the **outer** approximation (the polytope
`{z | Az ≤ b}` no cut has excluded yet) directly. That's a superset of the
true near-optimal space — much of its volume isn't actually confirmed
near-optimal, only "not yet ruled out" — so a chunk of what got plotted
wasn't a real near-optimal design, and in projections the sample cloud
visibly pulled away from the real certified points overlaid on it (which
read, misleadingly, as "the points are outside the sampled region," even
though every certified point legitimately satisfies the outer polytope by
construction).

Following `Steen2026_Thesis` Sec 3.3's rejection-sampling *idea* (Max Steen's
ORACLE application to a larger ZEN-garden model), the fix is **rejection
sampling**: walk the outer polytope cheaply, keep only proposals that also
pass the **inner** approximation's membership test (a small LP: is this
point a convex combination of certified near-optimal designs?). Every
accepted point is then a genuine certified near-optimal design, not just
"not yet excluded." The green outline is the *exact* 2D projection of the
inner hull (a linear projection of a convex hull is the hull of the
projected vertices, so this isn't an approximation either).

*Correction:* an earlier version of this note claimed this script shares
"the same pyoNearOpt/PolyRound/Vaidya-walk machinery" as Steen's own
sampler. That overstates it. Steen's Sec 3.3 sampler is a hand-written
**hit-and-run** walk with covariance preconditioning for elongated bodies,
implemented independently of pyoNearOpt for the thesis. This script instead
calls pyoNearOpt's own `PolytopeSamples` helper with `walk_type="vaidya"`
(the package default; see `near_optimal_tools/docs/using_the_package/sampling_and_diagnostics.rst`).
Vaidya and hit-and-run are both valid MCMC walks that make the same
rejection-sampling idea (Steen's Eq. 13, same acceptance-rate diagnostic)
work — but they are different algorithms, and only the *idea*, not the
implementation, is shared with the thesis.

Sampling is cached in
`data/outputs/euler_outputs_mga/mga_inner_sampling/` and only re-runs if the
underlying polytope changes (new probabilistic data) or the sample settings
change.

**What the data says.**
- Acceptance rate: **25,304 / 30,000 proposals (84.4%)** — this estimates
  vol(inner)/vol(outer) for probabilistic-**long's** polytope (129
  iterations under a strict `tolerance_prob=0.95` bar). That is a dramatic
  jump from what the same acceptance-rate check gave on the short run's
  9-iteration hull (6.8%, see the git history of this file): after 129
  iterations, the certified inner hull has come to occupy most of the outer
  box's volume, not a small sliver of it — direct, quantitative confirmation
  of what the table above already showed via `ci_lower` (0.94, just short of
  the 0.95 target). This is well above Steen's own 700-iteration, 10-D
  ORACLE certificate (11.6%) — not the same order of magnitude — consistent
  with this run's stricter convergence target and lower dimensionality (6-D
  vs. his 10-D) pushing it much closer to full coverage, not a sign anything
  about the geometry here is unusual.
- The green outline (probabilistic-long's own certified hull) now visibly
  tracks most of the explored point cloud in most panels, unlike the earlier
  short-run hull, which sat well inside it. Checking membership directly:
  139 of probabilistic-long's own 140 points trivially satisfy it (99%,
  as expected — they built the hull), but only 10/96 (10%) of oracle's
  points and 10/20 (50%) of probabilistic-short's own points formally pass
  the same exact convex-combination test. In both cases the 10/96 or 10/20
  that *do* pass are exactly the 11 shared VMM/baseline points minus one
  numerically-borderline case (`max:biomass`), which match long's own
  to full floating-point precision and score as inside cleanly; every one
  of oracle's 85 reconstructed iterations and probabilistic-short's own 9
  refinement iterates score as outside. This is expected, not a
  contradiction of the 84% coverage figure above: coverage is a volume
  statistic over the whole box, while hull membership is an exact test
  against long's own *specific* 140 vertices — oracle's stuck cluster and
  probabilistic-short's independently-sampled directions are different
  (still individually valid) near-optimal designs that a different, later,
  more thorough search never happened to certify itself.
- Most axes have right-skewed marginals — most of the near-optimal volume
  sits at low-to-moderate capacity, with a long thin tail toward the
  certified maxima (matches Steen's finding on his larger 9-axis space).
- **Cost tells the clearest story, now with 12x more interior samples than
  before.** Only 0.33% (84 of 25,304) of interior samples land above 94% of
  the cost budget, and none reach 99% (median sits at 81% of the budget:
  p5=63%, p50=81%, p95=91%; max observed = 96%). Compare that to fig1, where
  weights/oracle/probabilistic-short still sit at ~100% of the budget most
  of the time, and even probabilistic-long's own certified vertices sit
  above 95% of budget half the time. In other words: a typical near-optimal
  design uses only part of the available cost slack — it's specifically the
  extreme, boundary-pushing designs that directional/bilevel/short-sampled
  searches are structurally biased toward finding that spend the full 10%.
  This is a structural fact about the shape of the polytope (a
  simplex-like cost-cut region where extremes concentrate at the cost cap),
  not a quirk of any one method — and now backed by a hull covering 84% of
  the outer box rather than 7%.
- Biomass skews the other way — the sample density concentrates toward
  *high* biomass import (median at 65% of the range), mirroring the
  baseline's own choice to import at the dataset's limit.


## fig3 — pairwise Pearson correlation over the same interior sample

**What it shows.** How the near-optimal *volume* trades axes off against
each other: negative r means the two axes substitute (more of one goes with
less of the other across near-optimal designs), positive means they move
together. This needs the same interior sample as fig2 (probabilistic-long's
hull), not just the certified vertices, because it's a statement about the
shape of the space, not about any one design (cf. Steen2026_Thesis Figure 7,
same method). Reported on physical units purely for readability — Pearson r
is invariant to per-axis affine rescaling, verified here directly: computing
it on the raw normalised (0-1) coordinates instead gives the same matrix to
1e-14, so normalisation is not why any pair looks correlated.

**What the data says — and how it changed from the short-run hull.** With
129 iterations' worth of certified points behind the sample instead of 9,
several correlations that looked strong on the earlier, much sparser hull
turn out to have been overstated; a few others emerge that weren't visible
before.

- **Photovoltaics vs. wind onshore, r = −0.43** — still the strongest single
  coupling, the two dominant variable-renewable technologies substituting
  under a fixed cost budget (physically sensible, and the same substitution
  fig0's weights-mode bars showed directly for two single solves) — but
  markedly weaker than the −0.71 the short-run hull reported. A large part
  of that earlier value was likely an artefact of having only ~2,000
  interior samples drawn from a hull built on 9 certified points; 129 points
  fill in the space between the extremes that dominated the earlier read.
- **Wind offshore vs. net present cost, r = +0.31** is now the strongest
  link any technology axis has to cost — a finding that didn't show up at
  all on the short-run hull, where **nuclear vs. cost (r = +0.35)** held
  that role. On the long-run hull, nuclear vs. cost drops to a weak +0.08;
  it's wind offshore's capital cost, not nuclear's, that shows up most
  clearly as eating into the slack once far more of the space is
  characterised.
- **Nuclear vs. biomass, r = +0.25**, and **wind offshore vs. biomass,
  r = +0.21** — both essentially invisible on the earlier hull (biomass was
  reported as "nearly uncoupled from everything," |r| ≤ 0.10 against every
  axis). With more of the space sampled, biomass turns out to have real,
  if modest, co-requirement with both nuclear and wind offshore.
- **Photovoltaics vs. wind offshore, r = −0.31**, and **wind offshore vs.
  wind onshore, r = −0.26** — wind offshore is now the second-most-coupled
  axis overall, a role the earlier hull assigned to wind onshore's coupling
  with nuclear (r = −0.32 then; r = −0.15 now).
- No pair reaches |r| > 0.43 on this much better-characterised hull (down
  from 0.71), and every pair now sits below 0.32 in magnitude except the
  top one: the near-optimal space here reads as more weakly coupled overall
  than the short-run hull suggested, closer in character to Steen's finding
  on his larger axis set (his strongest pair was −0.45) than the earlier
  read implied.

The practical takeaway: correlations computed from an early-stage,
sparsely-sampled polytope (probabilistic-short's 9-iteration hull) can be
materially misleading about the true shape of the near-optimal space, not
just noisier — several relationships flip which axis pair is "strongest" or
"most coupled to cost" once ~14× more certified points are behind the
sample. This is itself a useful argument for `tolerance_prob`: a loose
convergence bar is cheap, but conclusions drawn from its hull about the
*shape* of the space (as opposed to just a handful of extreme points) should
be treated with real caution.


## fig4a/fig4b — model queries and cumulative solving time

**What these show, and a layout correction.** Two figures, matching
`near_optimal_tools`'s own `docs/examples/method_comparison.ipynb` layout
**exactly**, column for column: `fig4a_query_comparison` corresponds to the
reference's `method_comparison.png` (x = number of model queries),
`fig4b_time_comparison` to `method_comparison_time.png` (x = cumulative
solving time, log). In both, the **left column is `max_separation`** (the
oracle-style worst-case L∞ distance between inner and outer approximation,
log scale, lower is better) and the **right column is
`fraction_well_explored`'s `ci_lower`** (the 95%-CI lower bound on the share
of sampled directions already within `tolerance_explore` of the outer
approximation, higher is better) — same as the reference. An earlier version
of this figure put the x-axis choice (queries vs. seconds) in the columns
instead, with the metric in rows. That showed the same four numbers but
could not be read side by side against the reference's own two PNGs the way
this layout can; it has been corrected to match column-for-column.

The reference makes one *row* per test-problem dimensionality (its "case":
3-D, 6-D, 9-D toy problems). This project has only one real problem — the
6-D MGA space — so that row grouping is repurposed for **which outer
approximation each mode is scored against** instead:

- **Row 1 (frozen initial box).** Every available mode (weights,
  probabilistic-short, probabilistic-long, oracle), scored against the
  shared, un-cut initial VMM box the whole time (`poly.A/b` up to
  `n_initial_rows`) — this project's own choice, needed because oracle's own
  cut history was lost (data-loss note above) and weights never builds an
  outer approximation at all, so this is the only evaluation all four modes
  can be scored on equally. This is **not** what the reference notebook
  does, and not the same quantity as each run's own native `ci_lower` in the
  tolerance-comparison table further up this document.
- **Row 2 (own evolving approximation) — the actual reference methodology.**
  Only probabilistic-short and probabilistic-long, each scored against
  *its own* live, cut-refined outer approximation at each checkpoint — i.e.
  exactly what the reference notebook's `score_run` does for every method
  (it keeps a full A/b/X snapshot per iteration and re-scores it after the
  fact with one shared evaluation config). Oracle and weights cannot appear
  in this row: oracle's own cut-by-cut history is gone with its lost
  `oracle_summary/`, and weights never builds an outer approximation at all
  — see the text box drawn directly on the figure.

**How row 2 was reconstructed, and why it can be trusted.**
`supf_explore.explore` (the probabilistic driver's inner loop) calls
`poly_approx.add_point(new_point)` and
`poly_approx.add_cut(direction, support_value)` exactly once per iteration,
and each run's own `diagnostics.csv` logs precisely those two raw arguments
every row. Replaying them in order — starting from the same initial VMM box
used for row 1 — reconstructs each iteration's own live outer approximation
exactly. This was verified directly, not just argued: replaying
probabilistic-short's full cut history this way and comparing the result
against its own saved *final* `polytope.npz` gives bit-for-bit the same
feasible region (same row count, and 20,000 random test points agree on
which polytope contains them, every time). Row 2's dashed lines are each
mode's own real `tolerance_prob` target (0.05 short / 0.95 long, colour-
matched) on the `ci_lower` panel only — there is no equivalent target line on
the `max_separation` panel, unlike the reference's ORACLE-specific `tol`
line: probabilistic mode never targets an exact worst-case separation bound,
only the sampled-direction confidence interval.

**A read note specific to fig4b (vs. solving time):** oracle's line does not
start at 1.0 there like every other mode's does — it starts at its first
real solve, ~684 s in (max_separation ≈ 0.688, its value at query 11). That
is not a bug; oracle's own baseline point (the one that *is* at
max_separation = 1.0) is the shared frame's z\*, borrowed because oracle's
own baseline result folder was lost (see the data-loss note above) — no real
ZEN-garden solve backs it, so it has no logged solving time and cannot be
placed on a log time axis at all. It still appears correctly at query 1 in
fig4a, where x=1 is a perfectly good linear-axis value. (An earlier version
of this figure did not filter zero/NaN-time points before plotting fig4b,
which let matplotlib silently drop just that one point — same net visual
effect, but for the wrong reason: it looked like oracle's *second* point had
been dropped too, when only the untimed first one had. The reference
notebook filters this explicitly for exactly this reason; this script now
does too.)

### Row 1 (frozen box): what the data says

(endpoint values; see the figures for the full trajectories)

| mode | queries | cumulative solving time | max separation: start → end | frozen-box ci_lower: start → end |
|---|---|---|---|---|
| weights | 7 | 596 s (~10 min) | 1.000 → **0.953** | ~0 → **0.022** |
| probabilistic (short, τ=0.05) | 20 | 2,212 s (~37 min) | 1.000 → **0.621** | ~0 → **0.024** |
| oracle | 96 | 34,297 s (~9.5 h) | 1.000 → **0.647** | ~0 → **0.032** |
| probabilistic (long, τ=0.95) | 140 | 24,762 s (~6.9 h) | 1.000 → **0.604** | ~0 → **0.156** |

- **Weights barely moves the metric at all** — 6 directional solves shrink
  the worst-case gap by less than 5%. It was never designed to close this
  kind of gap; it was designed to produce a few maximally-different
  boundary designs cheaply, which it does (fig0), just not to characterise
  the space's coverage.
- **Oracle and both probabilistic runs start identically** (all reach 0.688
  at query 11, right after their shared VMM points) **and then diverge
  sharply.** Oracle is already down to 0.647 by its next checkpoint (query
  21) and then **does not move again**: every checkpoint from query 21
  through query 96 changes the metric by less than 0.001 — its 10 iterations
  between checkpoints, and per the exact-duplicate check above most of the
  85 individual iterations behind them, did essentially nothing. Both
  probabilistic runs keep improving checkpoint over checkpoint instead: the
  short run reaches 0.621 by query 20; the long run is at a closely
  comparable 0.618 one checkpoint later (query 21) before continuing for
  another 119 queries: 0.607 (query 51) → 0.604 (query 140), with visibly
  diminishing returns after roughly query 60.
- **On this frozen, deliberately-hard box, even the long run's `ci_lower`
  stays low (0.156) and looks nowhere near converging.** That is expected
  given how the box was chosen (see the paragraph above), *not* a sign that
  anything is wrong with the run or its inputs — row 2 below is the fair
  question to ask about that, and answers it very differently.

### Row 2 (own evolving approximation): what the data says

| mode | max separation: start → end | own `ci_lower`: start → end | own `tolerance_prob` target |
|---|---|---|---|
| probabilistic (short, τ=0.05) | 1.000 → **0.482** | ~0 → **0.052** | 0.05 (cleared) |
| probabilistic (long, τ=0.95) | 1.000 → **0.105** | ~0 → **0.926** | 0.95 (not yet cleared, but close) |

This is the row that actually answers **"why does the long run's
`ci_lower` stay so low — is something wrong?"** On its own evolving,
cut-refined approximation — the correct, reference-equivalent question, and
the one the run's own stopping rule actually asks — probabilistic-long's
`ci_lower` climbs to **0.926** by query 140, a hair under its own 0.95
target (and closely matching the 0.940 already reported from its own native
`diagnostics.csv` in the tolerance table above — the small gap is just
because this recomputation uses a fixed, shared evaluation config —
500 samples, seed 0 — for comparability with row 1, rather than the run's
own 2,000-sample setting). Nothing is wrong with the inputs or the run: the
frozen-box version in row 1 was always going to look far less converged,
because it is evaluated against a box that never shrinks, no matter how much
real refinement the run has done.

The same swap also resolves how much of row 1's short-vs-long conclusion
survives the correct comparison. On their own approximations, `max_separation`
drops far further for both runs than on the frozen box: short reaches 0.482
(vs. 0.621 frozen) and long reaches **0.105** (vs. 0.604 frozen) — an order-
of-magnitude-scale difference for the long run in particular, since its own
outer approximation has been cut down substantially over 129 iterations
while the frozen box never moves. Tightening `tolerance_prob` from 0.05 to
0.95 now clearly earns its cost on both metrics, not just `ci_lower`: 0.482
→ 0.105 in max separation (long ends up **more than 4× tighter**), for the
same 7×-queries / 11×-time premium already noted above. Read together, rows
1 and 2 tell complementary stories: row 1 is the fair *cross-mode* picture
(all four methods judged by the same fixed yardstick, at the cost of
understating every mode's true progress against its own approximation), and
row 2 is the fair *per-run* picture (each run judged on its own terms,
matching what the reference notebook itself measures, at the cost of only
covering the two modes whose cut history survives).

- Practically, oracle still spent **~40% more solving time than
  probabilistic-long** (9.5 h vs. 6.9 h, row 1's only fair cross-mode
  time comparison, since oracle has no row-2 equivalent) and ended up at a
  **worse** frozen-box value (0.647 vs. 0.604) — not because oracle wasted
  time on a metric that had already plateaued, but because it got stuck
  re-certifying one vertex 73 times in a row and so never got the chance to
  keep improving the way both probabilistic runs did with their own
  comparable query budgets.
